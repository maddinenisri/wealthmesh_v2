## Recommended operating changes

1. Define a small outcome and changed-file scope before assignment. Use the existing clock to record start/deadline, a checkpoint at eight minutes if still working, and a safe stop by ten. Report completed/remaining work, actual commands/exits and resource/dirty state in the existing packet. No new timer infrastructure or automatic renewal of the same unfinished assignment.
2. Reuse accepted UX/architecture for routine changes within the approved baseline. Record the delta; involve those roles only for changed screens/contracts/invariants or material choices. A new feature still has a concrete design and pre-code validator plan reviewed by the owner.
3. Show one real vertical slice early after design approval. Check the actual request through UI, service and PostgreSQL before multiplying forms/scenarios. Reuse shared form actions, error helpers and layout patterns purposefully; verify the visual target during design rather than discovering it at acceptance.
4. Let independent validator/reviewer investigate stable code concurrently with exclusive scopes. Serialize writing to the feature packet and commands that share mutable outputs. Consolidate known findings into one correction batch, then rerun affected checks on the corrected revision.
5. Use about five readable acceptance groups with full underlying scenario coverage. Select changed-area checks; preserve earlier evidence for unchanged areas. Budget long commands explicitly as bounded assignments, mark unfinished execution pending, and never run historical full setup verification just to produce another notification.

Keep TDD, separate role sessions, Testcontainers, MSW isolation, real E2E and exact-money/date/ownership invariants. Two human checkpoints remain. Full original scenario completion still requires every original assertion; feature acceptance cannot complete deferred clauses. No v3 adoption, source migration, infrastructure refactor or finance scope choice is made here.

### Scope and evidence are different

V3's board/feature notes say **partial: five IDs covered, two deferred**. Its deferred register excludes CHECKING_002 whole because salary is unavailable, while zero-start is tested without that ID; CHECKING_006 remains blocked. The current checking UI offers one owner, deferring joint-member UI. These boundaries are narrower than accepted v2 FIN-001. V3 owner answers Q-008/Q-010 explicitly accept structural opening-income proof and inactive future actions: inspected UI disables money-in/out/transfer and opens Update balance with disabled Save. These decisions belong to v3. Its API test has a comment explaining structural income separation, not an executed monthly-income assertion. Before changing any v2 coverage claim, map every original clause, adapted acceptance and establishing evidence explicitly; an ID citation cannot make deferred behavior complete.

`scripts/scenario-coverage.sh` counts a whole-token ID appearing **anywhere** in backend test sources, all `frontend/src`, or E2E test files. Whole-token matching avoids confusing `_001` with `_0010`, but comments/implementation text can still count. It does not inspect assertions, example rows, test layers, execution/skips, tested revision or whether all original clauses pass. A matching bare deferred ID is accepted without validating its reason; an ID citation takes precedence over a deferral. A filter matching no feature files produces zero missing and can return success. Its self-test verifies token/filter/deferred mechanics, not behavioral completeness. Thus “5/7 covered, 2 deferred, 0 missing” is textual traceability/readiness, not independent proof. V2 keeps explicit full/partial/deferred mapping and actual required evidence; mandatory approved checks are never automatically deferred.

The transcript reports a validator interval of **5m 42s**, not whole-feature duration. A concrete boundary shows why assertion review matters: v3 `money/Money.java` permits 17 whole digits and `V2__accounts.sql` stores `NUMERIC(19,2)`. `AccountDetailPage.tsx` converts both amount strings using `Number(...)`; design-system `Amount.tsx` accepts a number and formats it with `Intl.NumberFormat`. This is source inspection plus numeric-expression reproduction, **not a live UI, API or database test**, and no v3 fix was made. ID counts and ordinary-amount journeys cannot by themselves establish exact display at the supported boundary; v2 retains its own approved money range and financial assertions.

### Rules not adopted

Do not import v3's 20–30-minute build groups, 15-minute automatic scenario deferral, repeated planted-failure ceremony, full historical suites after every small change, or `git checkout -- <file>` on a dirty tree. Keep v2's ten-minute assignments, pre-code independent validator plan, separate final reviewer, exact-money/integrity constraints and both human checkpoints. V3's commit-only-when-asked rule does not replace v2's standing normal commit/push authorization. No role merger, reactive migration, changed feature acceptance or original completion is approved. FIN-002 remains design pending; only compatible compact planning/runbook improvements are applied.
