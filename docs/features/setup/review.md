### IR-01: environment overrides can redirect migration or server binding

Status: **closed: source correction and independent configuration-isolation evidence checked**. Owner: backend developer for fixture protection; platform developer for development launcher. Scenarios: AC-02, AC-03, AC-08, AC-10.

`backend/src/testSupport/java/com/wealthmesh/testsupport/BackendFixture.java:25` starts the real application with command-line datasource URL/username/password and port. This correctly overrides generic datasource environment values. It does not override or reject independent `spring.flyway.url`, Flyway credentials/configuration, or `server.address`. `scripts/paths.mjs:24` inherits the complete parent environment. `scripts/runtime.mjs:84` sets `WM_*` values and launches the JAR without authoritative Spring command-line arguments. `backend/src/main/resources/application.yaml:1` fixes loopback only at the configuration-file priority.

Spring environment configuration has higher priority than configuration files. For example, inherited `SERVER_ADDRESS=0.0.0.0` overrides the YAML address; inherited `SPRING_DATASOURCE_URL` overrides the YAML `WM_DB_URL` interpolation for development. More critically, `SPRING_FLYWAY_URL` can direct migrations to a distinct database despite the disposable datasource URL CLI arguments. Existing isolation tests examine explicit image-file configuration only; they do not protect this independent migration connection.

Primary-source verification: [Spring Boot 4.1.1 external configuration order](https://docs.spring.io/spring-boot/reference/features/external-config.html) places environment/system/JSON properties above config files and command-line values above those. [Spring Boot Flyway initialization](https://docs.spring.io/spring-boot/how-to/data-initialization.html) documents that an explicit Flyway URL or user creates its separate connection, with missing settings falling back to the datasource settings. These sources confirm the code-based finding; no unsafe external connection was attempted.

Required correction: make the supported launcher/fixture connection and bind boundaries authoritative or reject conflicting environment/configuration sources before startup. Ensure Flyway shares the owned datasource and cannot use a separate inherited connection. Add meaningful regression coverage for stale datasource settings, independent Flyway settings and non-loopback address overrides using only synthetic/disposable targets; do not attempt migration against the development database to reproduce the issue. Refresh affected backend/platform checks and report effective connection/bind evidence. Review configuration-file imports/locations and JVM environment options as part of the same explicit configuration precedence boundary; document supported overrides narrowly.

Checked correction: `BackendFixture.ownedEnvironment` removes parent system-property/environment sources, restricts config to packaged `classpath:/application.yaml`, and supplies only owned connection and loopback port. `FixtureConfigurationIntegrationTest` verifies actual HTTP readiness, the effective owned database/address and object identity between Flyway's datasource and the application datasource. The refreshed [backend evidence](backend-implementation.md#independent-review-correction-implemented-ir-01) reports 3 unit/11 integration tests and strict checks passing with synthetic hostile environment/system/JSON/config values. Backend fixture correction is source-checked and developer evidence is reconciled, awaiting independent execution.

That residual was recorded here and then corrected: `scripts/application-configuration.mjs` supplies `--spring.config.location=classpath:/application.yaml` and `--server.address=127.0.0.1`, and `scripts/runtime.mjs` uses that same builder for the actual development JAR. `scripts/launcher-check.mjs` uses the production builder from a disposable cwd containing hostile root/config YAML and only a deliberately absent synthetic database target.
