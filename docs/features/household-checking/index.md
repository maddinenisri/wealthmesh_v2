## Recommended behavior and boundaries

One usable slice creates/renames a household, adds named members with optional distinguishing labels and creates checking with individual or joint owners, name, bank, initial USD amount and financial date. Show household creation, empty overview, account list and detail; preserve data across reload. Count a shared checking account once in the clearly labelled checking-only household amount; do not imply totals include unimplemented account types.

Blank/explicit zero amount starts at zero. The owner's D-027 answers permit overdrafts and plain/grouped dollar text, reject excess precision without rounding, and use backend local today or an earlier date. Checking date coverage adapts the original savings scenario. Duplicate names use distinct name-and-label pairs in the proposed contract. Detail edits change name/bank/owners without changing money/date; cancellation before submission saves nothing. Invalid name/amount preserves entered fields. Starting amounts establish balances, not income; the plan establishes that boundary without claiming salary or monthly-income behavior exists.

Defer activity, transfers, savings/cards/investments, budgets, Update balance/corrections, legacy recovery, member rename/deactivation/restoration/full profiles, account archive/delete/undo. Deferred means retained for later scope, not deleted globally. UX must explain unavailable future actions without enabled nonfunctional buttons.

### Authoritative rules and exact values

One household exists per installation. Create/rename household and add member are independent saves; cancelling checking does not undo either. Names are required after normalization, limited to 120 Unicode code points; optional bank is limited to 120, with blank stored as null. Normalize names using Unicode NFC, trim outer whitespace and collapse runs of whitespace to one space. Derive name comparison keys with Java `toLowerCase(Locale.ROOT)` after that normalization; accents and punctuation remain meaningful, with no fuzzy matching. Account names need not be unique, so two genuine accounts at a bank may share a label. Display saved owners in member creation order, using ID as a deterministic tie breaker. Ownership is by UUID, never by editable display text.

The distinguishing label is an optional separate string, normalized by the same NFC/whitespace rule, limited to **80 Unicode code points** and stored as null when omitted/blank. Its comparison key is lowercase normalized text, or the empty string for null. Uniqueness applies to `(household_id,name_key,label_key)`, not `name_key` alone. Thus Sam with no label, Sam with Parent and Sam with Child are three distinct annotations; `sam`/`PARENT` conflicts with Sam/Parent, while Maya/Parent and Sam/Parent are allowed. An unlabelled member may coexist with a labelled same-name member; there can be only one unlabelled member for that normalized name. Do not retroactively rename or label existing members when another is added. Member rename/label edit remains deferred, so adding a second same-name member must work by entering its distinct label now.

API results return `name` and `label` separately. Render the name and, when present, a visually separate **Label: Parent** badge/text in household members, owner checkboxes, account rows and detail. Accessible owner labels identify both fields (for example **“Name: Sam; Label: Parent”**); an unlabelled Sam is **“Name: Sam”**. Do not concatenate a label into the stored name or use display text as an ID. This preserves distinguishable structured fields even when someone's name contains punctuation used by presentation. Adding a member with a duplicate pair rejects without a write, focuses the label field and retains both inputs. Adding another label creates a different member UUID; repeating the same create UUID compares both normalized fields for safe recovery.

USD is the only currency. Java parses the raw amount string centrally into a `BigDecimal`-backed immutable money value. Trim outer whitespace, allow an optional leading `-`, then an optional `$`, then either ungrouped ASCII digits or an initial group of one to three digits followed by comma-separated groups of exactly three. A decimal point, if present, requires one or two following digits. Reject `+`, parentheses, exponent notation, internal spaces, malformed grouping, `.50`, `5.`, and non-USD symbols. Blank/null means zero; JSON numeric inputs are rejected. `-0.00` normalizes to `0.00`. Never construct money from `double` or JavaScript `Number`.

Each opening amount must be within **-$999,999,999,999.99 through $999,999,999,999.99**. Count fractional digits before conversion and reject even `1.000`; after validation use scale 2 with `RoundingMode.UNNECESSARY`. PostgreSQL stores `NUMERIC(14,2)`; application validation happens before SQL because that column type alone can round oversized fractional input. No rounding operation is required by this feature. API money responses are canonical decimal **strings**, for example `"5000.00"`, with `currency: "USD"`; no currency symbols or commas in responses. Frontend validates these strings and formats digits exactly without monetary floating-point arithmetic.

Balance equals the saved opening amount because this slice has no financial activity or corrections. The checking total is an exact backend sum over checking-account rows, **never over the owner join**, with no-account sum explicitly zero. It may exceed the single-account limit, so do not narrow the sum to `NUMERIC(14,2)` or impose that limit on aggregate response parsing. Both owners see one account; editing owners cannot duplicate its money. Do not create income, expense, transfer or opening-activity records; no monthly-income calculation/API is proposed. “Starting amount is not income” is established here by that storage/classification boundary, not by a nonexistent income screen.

Financial dates are strict `YYYY-MM-DD` strings, valid Gregorian dates with a four-digit year from 0001 through 9999, mapped to Java `LocalDate` and SQL `DATE`. They are never converted through a UTC instant. Creation always stores a date, including zero/blank amounts. The backend provides `today` and `financialZone` when loading household data; inject a controllable Java `Clock` for tests. Configure the financial zone using `WM_FINANCIAL_ZONE`, defaulting to the backend computer's system zone; the expected setting here is `America/New_York`. Invalid zone configuration fails clearly at startup. Future-date validation uses the backend date at submission; once a draft date is set, do not overwrite it during a midnight refresh. `createdAt` and `updatedAt` are separate UTC timestamps mapped to `TIMESTAMPTZ`, for diagnostics/concurrency, not financial meaning.

### API contract

Use the existing same-origin `/api` proxy and loopback binding. UUIDs are strings. Reject malformed UUIDs, unknown command fields and wrong runtime types with field feedback; an edit request containing money/date must be rejected rather than silently ignored. Responses use explicit transport records, not database entities. `Account` is `{id, type:"CHECKING", name, bank:null|string, owners:Member[], currency:"USD", balance:string, balanceDate, version, createdAt, updatedAt}`. `Household` is `{id,name,version}` and `Member` is `{id,name,label:null|string}`. Versions are positive integers used to reject stale edits.

| Operation                        | Request                                                                   | Successful response and meaning                                                                                                                                                                                                                              |
| -------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/household`             | None                                                                      | `200 {household:null\|Household,members:Member[],accounts:Account[],checkingTotal:{currency:"USD",amount:string},today,financialZone}`. Only a successful response with null household means first setup; arrays are empty and total `"0.00"` in that state. |
| `POST /api/household`            | `{id,name}`                                                               | `201 Household`; the client supplies the draft UUID. A second household is a conflict, not another installation.                                                                                                                                             |

A failed owner insert, uniqueness conflict or database exception rolls the whole command back, leaving no account or partial owner set. The service enforces at least one owner before any insert/replacement, and the transaction preserves that invariant across all supported write paths. An ordinary FK/check constraint cannot prove a child row exists, so the join-table design does **not** claim database-level nonempty ownership enforcement. No direct SQL editing is an operating workflow. Test the service's invariant and rollback against real PostgreSQL; add no trigger framework for hypothetical external writers. ### Repeat requests, cancellation and errors

At form creation allocate one client UUID for each household/member/account create draft; retain it with that draft through failures and retries. This is the resource's primary key, not a generic request ledger. For an existing UUID, compare the normalized create values: if they match the saved resource, return `200` with that resource and do not insert or overwrite. A different payload using that UUID returns `409 CREATE_ID_CONFLICT`; never apply it as an edit. If details were subsequently changed, the create retry may conflict; the user must open the saved resource rather than recreate it. Concurrent identical creates converge via the unique primary key and a read after the losing transaction rolls back. Equivalent `"5000"`/`"$5,000.00"` amounts compare as the same money.

After a lost create response, keep the draft ID, show the UX's honest uncertain-save message and offer **Check saved result**. Checking household/account by the stable ID (household via the overview) can confirm a committed save. Member reconciliation uses that ID in the member list. If present, open/announce the saved record without a second create; if absent on a successful read, allow retry of the **same ID**. A temporarily absent record does not prove a still-running original request cannot commit; stable-ID retry remains safe. A reload may discard the draft ID, so the initial overview/member-list recovery must expose existing records; do not automatically resubmit abandoned drafts. Duplicate submission is disabled while pending.

Cancel before submission makes no request. During submission/uncertain completion, do not label abandonment as cancellation of a committed request: retain/reconcile the result first. After a confirmed save failure, cancel discards the draft without writing. Unsaved navigation warnings and focus follow UX. Edits use `expectedVersion`; stale tabs receive `409 STALE_VERSION`, retain the draft, and offer loading current saved details before a deliberate new edit. A lost edit response is reconciled by rereading details and comparing the intended fields; retry with a stale version cannot overwrite a later edit.

Feature errors have `{code,message,fieldErrors:[{field,code,message}],requestId,saveOutcome}`. `saveOutcome` is `NOT_SAVED` only when rejection or completed rollback is known; otherwise `UNKNOWN` requires reconciliation. Use `400 VALIDATION_FAILED` for invalid fields/types, `409` for singleton/create-ID/stale-version conflicts and **`409 MEMBER_IDENTITY_CONFLICT`** for a duplicate normalized name-and-label pair (field `label`), `404 ACCOUNT_NOT_FOUND`, `503 FINANCE_UNAVAILABLE` for database dependency failures and `500 INTERNAL_ERROR` for unexpected failures. Network failure, timeout or malformed response is always uncertain for a command, regardless of apparent HTTP status. Request correlation is diagnostic, separate from the create resource ID.

Keep required wording **“Enter an account name”** and **“Enter a valid amount”**; amount precision/range errors add helper explanations rather than clear raw input. Ownership, bank/name/label length, duplicate member pair and date errors identify their fields. Label overflow says **“Use 80 characters or fewer for the distinguishing label.”** Database errors never become a success-shaped zero/empty response. Log request ID, operation, result, duration and safe exception classification; do not log payload names, labels, amounts, credentials or SQL parameter values. Respond without SQL/stack traces. A correlation ID lets the owner match a screen error to the existing backend log.
