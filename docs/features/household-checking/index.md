### Exact money, dates and ownership

USD only. One authoritative Java parser constructs an immutable `BigDecimal`-backed money value from **text**, never floating point. Trim outer whitespace; accept an optional leading minus, then optional `$`, then ungrouped ASCII digits or a one-to-three-digit first group followed by comma groups of exactly three, then an optional decimal point with one or two digits. Blank/omitted/null starts at zero; accept `5000`, `5000.0`, `$5,000.00`, `-125.50` and `-$125.50`. Reject numeric JSON, `five thousand`, `+`, parentheses, exponents, internal spaces, foreign symbols, malformed commas, `.50`, `5.` and excess places including `1.000`. Preserve raw failed input. Normalize negative zero to `0.00`.

Opening amounts range from **-$999,999,999,999.99 to $999,999,999,999.99**. Validate precision/range before SQL, then set scale 2 with `RoundingMode.UNNECESSARY`; PostgreSQL `NUMERIC(14,2)` alone can round fractional input and must not be relied upon for rejection. No rounding operation is needed. Responses carry canonical decimal strings such as `"5000.00"` and `currency:"USD"`. Frontend runtime-validates them and formats digits without JavaScript monetary arithmetic. Overdrafts display a minus and reduce the total.

Balance equals opening amount in this slice. Sum the distinct account records exactly in Java for the checking total; never sum an ownership join. No-account total is `"0.00"`. The total may exceed an individual account's range, so do not constrain it to `NUMERIC(14,2)` or a single-account response limit. Joint ownership counts once; owner edits do not move money. Create no income/expense/transfer/activity records or monthly-income result. This establishes opening-balance classification, not deferred income-report assertions.

Dates are strict `YYYY-MM-DD` Gregorian dates, years 0001–9999, represented by `LocalDate` and SQL `DATE`, never a UTC instant. Default to the **backend computer's system-zone today**, initially America/New_York; allow today/earlier, reject future dates using backend today at submission. Inject `Clock` for tests. Return `today` and `financialZone` with household data so the browser does not substitute its clock. Keep an entered draft date unchanged at midnight; zero/blank amounts still save a date. Use the existing machine/JVM timezone configuration, with **no new finance-zone environment setting**. UTC `TIMESTAMPTZ` creation/update fields are diagnostic timestamps, separate from financial dates.

One household exists per installation. Names require nonblank normalized text, maximum 120 Unicode code points; bank is optional, maximum 120, blank stored as null. Normalize with Unicode NFC, outer trim and whitespace-run collapse. For member comparisons, lowercase normalized values using `Locale.ROOT`; accents/punctuation remain meaningful. Account names need not be unique. Owners must be a nonempty set of distinct existing member UUIDs in the same household. Return them in member creation order, UUID tie breaker; never identify or transfer ownership by name.

### Persistence, atomic saves and ordinary coherent reads

Add the next forward-only Flyway migration after V1; preserve installation metadata and introduce no development household seed.

| Table                    | Main stored fields and constraints                                                                                                                      |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `household`              | UUID PK, singleton boolean fixed true with unique/check constraints, name, UTC timestamps.                                                              |
| `household_member`       | UUID PK, household FK, name, nullable label, normalized name/label keys, timestamps; unique household/name-key/label-key and household/member-ID pairs. |
| `checking_account`       | UUID PK, household FK, name, nullable bank, USD-only currency, non-null opening `NUMERIC(14,2)`, `DATE`, timestamps; unique household/account-ID pair.  |
| `checking_account_owner` | Household/account/member IDs; account/member composite PK; composite FKs ensure both references belong to the same household.                           |

Nonblank/length checks, not-null fields, uniqueness and restrictive FKs reinforce authoritative Java rules. The service ensures at least one owner before writes; ordinary constraints cannot ensure a child ownership row exists, so do not claim database-level nonempty ownership enforcement. No direct SQL editing workflow or speculative triggers.

Checking creation inserts the account and every owner link in one transaction. Account details update acquires that account's normal database row lock, updates allowed details, then replaces ownership links in the same transaction. Any failure rolls back the entire command, preserving previous complete state. Household rename and member text edit never update account money/ownership. Member-pair uniqueness rejects conflicting concurrent corrections atomically. A missing target is not success.

Use ordinary PostgreSQL READ COMMITTED queries.
